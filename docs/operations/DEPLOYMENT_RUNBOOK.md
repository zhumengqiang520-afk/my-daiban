# 部署上线与运维手册

本文是首版运行方案，实施时需结合实际云厂商、域名和备案条件补充具体命令。

## 1. 环境

必须分离：

- 开发：开发者本机，使用匿名样例数据。
- 测试：自动部署，允许重置数据。
- 预发布：配置尽量贴近生产，供 UAT 和迁移演练。
- 生产：只从版本标签部署，不允许人工改容器内文件。

## 2. 生产拓扑

试点建议：

- 1 台应用节点，起步 4 vCPU / 8 GB RAM。
- 托管 PostgreSQL 16 或独立数据库节点。
- 兼容 S3 的对象存储保存附件和凭证。
- Caddy/Nginx 提供 HTTPS、访问日志和上传大小限制。
- 云监控或 Prometheus 体系监控主机、应用和数据库。

实际容量在压测后调整。正式上线不要使用 SQLite，也不要把数据库和附件仅保存在容器临时文件系统。

## 3. 域名与安全

- 使用独立域名，例如 `tasks.example.com`。
- 中国大陆公网服务提前完成 ICP 备案等必要手续。
- 强制 HTTPS，HTTP 跳转 HTTPS，启用安全响应头。
- 管理入口不使用默认口令；首个管理员创建后立即轮换引导密钥。
- 数据库不暴露公网，安全组只开放必要端口。
- 生产环境限制调试端点和详细错误页。

## 4. 发布流水线

1. PR 合并后构建不可变 Docker 镜像，标签包含 Git SHA。
2. 生成 SBOM 和依赖漏洞报告。
3. 部署测试环境并执行自动化冒烟。
4. 创建 `vX.Y.Z-rc.N` 候选标签，部署预发布。
5. 完成 UAT、迁移演练和备份恢复验证。
6. 产品负责人批准后创建正式版本标签。
7. 生产先备份，再执行迁移和滚动/替换发布。
8. 观察登录、错误率、任务接口、通知和数据库至少 30 分钟。

## 5. 发布前清单

- [ ] 版本、提交 SHA 和镜像摘要已记录。
- [ ] 数据库迁移已在生产数据副本演练。
- [ ] 新增环境变量和密钥已配置。
- [ ] 当前生产数据库和附件备份成功且可读取。
- [ ] 回滚镜像和回滚/前滚数据库方案明确。
- [ ] P0/P1 缺陷符合上线门禁。
- [ ] 业务、开发、运维联系人在线。
- [ ] 变更窗口和用户通知已确认。

## 6. 回滚原则

- 纯应用问题：切回上一镜像，确认旧版本兼容新迁移。
- 可前向修复的数据迁移：优先修复迁移，不盲目回滚数据库。
- 破坏性迁移：停止写入，从发布前备份恢复，并按 RPO 评估数据补录。
- 任何生产手工数据修复必须有脚本、双人复核和审计记录。

## 7. 备份

- PostgreSQL：每日全量备份，条件允许时启用时间点恢复。
- 附件：对象版本控制或每日增量备份。
- 配置：加密备份非密钥配置；密钥由密钥管理系统备份。
- 保留建议：每日 14 份、每周 8 份、每月 12 份，根据合规要求调整。
- 每季度恢复到隔离环境，验证登录、任务、附件和审计记录。

## 8. 监控与告警

至少监控：

- HTTP 可用性、P95 响应时间、5xx 比例。
- 登录失败异常增长和权限拒绝异常增长。
- 后台任务积压、重复任务生成失败、通知失败率。
- CPU、内存、磁盘、对象存储和证书到期。
- PostgreSQL 连接数、慢查询、复制/备份状态。

告警必须包含环境、时间、影响、相关版本和排查入口。

## 9. 日常运维

- 每日：检查 P0 告警、备份、失败通知和任务生成。
- 每周：检查磁盘、慢查询、异常登录和积压 Issue。
- 每月：同步上游安全版本、依赖更新、权限抽查。
- 每季度：恢复演练、账号清理、权限复核和容量评估。

## 10. 事故处理

1. 确认影响范围，指定事故负责人。
2. 优先止损：关闭问题功能、限流或回滚。
3. 保存日志、版本和时间线，禁止先删除现场。
4. 向业务同步已知事实、影响和下一更新时间。
5. 恢复后 5 个工作日内完成无责复盘和改进 Issue。
