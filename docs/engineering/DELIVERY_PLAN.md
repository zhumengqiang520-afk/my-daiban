# 从需求到上线的交付流程

## 1. 团队职责

最小可行团队：

| 职责 | 建议投入 | 负责事项 |
|---|---:|---|
| 产品负责人 | 0.3 人 | 优先级、业务口径、最终验收 |
| 全栈工程师 | 2 人 | Go API、Vue 前端、迁移、集成 |
| 测试 | 0.5—1 人 | 测试设计、回归、门店 UAT |
| 运维/安全 | 0.2 人 | 环境、备份、监控、上线 |
| 门店代表 | 2—3 人兼职 | 场景样例、原型和试点反馈 |

一个人可以兼任多个职责，但“开发者本人验收自己全部工作”不可作为正式上线标准。

## 2. 时间表

以 2026-08-24 启动、双人开发为例：

| 日期 | 阶段 | 主要产出 |
|---|---|---|
| 08-24—08-28 | 需求确认 | PRD 基线、真实模板、权限名单、原型 |
| 08-31—09-11 | 技术底座 | fork、CI、环境、组织与权限 |
| 09-14—10-02 | 执行闭环 | 任务扩展、模板、今日待办、凭证、复核 |
| 10-05—10-16 | 管理闭环 | 负荷、提醒升级、看板、审计 |
| 10-19—10-30 | 门店试点 | 数据初始化、培训、两周真实使用 |
| 11-02—11-06 | 正式上线 | 迁移、发布、观察、验收与复盘 |

具体日期可因人员和节假日调整，但阶段退出条件不能省略。

## 3. 需求流程

1. 用一句话描述问题，而不是先指定页面或按钮。
2. 提供真实案例、当前做法、影响人员和发生频率。
3. 产品负责人写成 GitHub Issue，包含验收条件和数据权限。
4. 需求评审只判断价值、范围、风险和是否进入当前版本。
5. 开发前补充异常路径、埋点和上线/回滚要求。

需求准备完成（Definition of Ready）：

- 用户和业务问题明确。
- 验收条件可观察、可测试。
- 角色和数据范围明确。
- 依赖、设计稿或接口样例齐全。
- 优先级和目标版本明确。

## 4. 开发流程

采用短分支、Pull Request 和主干发布：

1. 从受保护的 `main` 创建 `feat/<issue>-short-name` 或 `fix/<issue>-short-name`。
2. 先写迁移和失败测试，再实现最小变更。
3. 本地通过格式化、静态检查、单元测试和前端构建。
4. 创建 PR，关联 Issue，说明数据迁移、风险、截图和回滚方式。
5. 至少一名非作者审核；权限、迁移和许可证变更需要指定审核人。
6. CI 全绿且验收条件通过后 squash merge。
7. 合并到 `main` 后自动部署测试环境；生产仅从签名版本标签发布。

完成定义（Definition of Done）：

- 验收条件全部通过。
- 新逻辑有自动测试，跨门店权限有负向测试。
- 数据迁移可重复执行并有回滚/前滚说明。
- UI 包含加载、空数据、失败和无权限状态。
- 日志、指标和审计事件满足排障需要。
- 用户文档和版本说明已更新。
- 已在测试或预发布环境由业务代表验收。

## 5. GitHub 管理规则

- 一个 Issue 只解决一个可验收问题；大型需求使用 Epic 清单关联。
- 标签建议：`type:feature`、`type:bug`、`area:retail`、`area:auth`、`priority:P0`、`status:blocked`、`security`。
- Milestone 使用 `v0.1-foundation`、`v0.2-mvp`、`v0.3-pilot`、`v1.0`。
- `main` 禁止直接 push，要求 PR、CI 和至少一次审核。
- 不把密码、顾客信息、生产截图或真实订单数据放进 Issue。
- 紧急修复也必须补 PR 和测试，不能长期保留服务器手工修改。

仓库已提供 Feature、Bug 和 PR 模板。

## 6. 测试与发布门禁

每个 PR：

- Go 单元测试与竞态风险检查。
- 前端 lint、类型检查、单元测试和构建。
- 数据库迁移从上一生产版本升级的冒烟测试。
- 关键权限和 API 契约测试。

每个候选版本：

- Chrome、Safari/移动 Safari、Android Chrome 主流程测试。
- 创建—执行—提交—驳回—重提—完成端到端测试。
- 多门店越权、安全上传和导出测试。
- 性能冒烟与备份恢复测试。
- 产品负责人在预发布签署 UAT 结果。

## 7. 试点安排

选择三家差异明显的门店：一家高客流、一家普通门店、一家人员较少门店。

试点前：

- 导入组织和员工，核对直属关系。
- 只启用 5—8 个高频模板，避免一次引入全部制度。
- 每个门店指定一名“超级用户”。
- 培训控制在 60 分钟，提供一页操作说明。

试点期间：

- 每天检查 P0/P1 问题、失败通知和未分配任务。
- 第 3 天和第 7 天各进行一次门店访谈。
- 不因为人员不熟悉系统而立即增加复杂功能，先区分培训、流程和产品问题。

## 8. 上线决策

满足以下条件才可正式上线：

- P0 缺陷为零，P1 缺陷有业务认可的规避方案。
- 权限测试、恢复演练和性能基线通过。
- 试点门店连续 7 天完成关键流程。
- 生产域名、HTTPS、备份、告警和值班联系人就绪。
- 用户、模板和初始权限清单由业务负责人签字确认。
- 回滚包和上一版本数据库备份可用。
- 通用审计能力所需的 Vikunja 许可证或经批准的替代基座已经落实。

## 9. 上线后

- 第一天和前三天分别进行运行检查。
- 第一周冻结大型新功能，只修复缺陷和数据问题。
- 两周后复盘目标指标、使用障碍和流程变化。
- 每月安排上游同步、安全更新和恢复抽检。
